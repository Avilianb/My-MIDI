## 已修复的问题

| 优先级 | 原问题与触发条件 | 修复 |
|---|---|---|
| P1 | 端口换绑、断线重连后，队列只保存 cable，旧手机 Note/CC 可以进入新归属端口。快速断开重连还可能被轮询漏过。 | 消息标记归属代次；连接、断开、订阅变化、换绑、NimBLE reset 均更新代次；消费者丢弃旧代次消息。 |
| P1 | 换绑执行 panic 后立即清音符状态，FIFO 满时尚未发出的逐音 Note Off 被清掉。挂载时也会先 panic 再清队列和状态。 | 清音改为持久待发送状态；成功写入才清对应位；挂载先清旧队列再安排清音。 |
| P1 | 丢弃 Note Off 后，新 Note On 入队会撤销旧 Off；另有旧 Off 消费时清掉更新的补发位的问题。丢失 Sustain/Button CC 释放也没有保护。 | 队列/FIFO 溢出使该端口旧积压失效并安排完整清音；恢复前抑制不完整按键序列，不再用“新 On 撤销挂起 Off”策略。 |
| P1 | Android 优先队列满、写入重试耗尽只弹错误；Write Without Response 的后续写回调没有被处理。可能留下永久卡音或死链。 | 单写者等待写完成回调，超时/失败/优先队列溢出时重建连接，由固件执行端口清音；恢复操作核对连接代次，避免误关新连接。 |
| P1 | App 发送最多 8 条消息的帧约 33 字节，默认 MTU 23 只允许 20 字节；连续帧丢最旧包可能丢掉某控件最终值。 | 连续发送按映射合并保留最新值；按协商 MTU 批量取消息，14-bit 对原子发送；按钮释放等优先 FIFO。 |
| P1 | 手动切端口会立刻把旧端口本地参数推入新端口；10ms 待发和底层队列仍可重放旧值。 | 切换不推本地快照；清理 Store 和传输队列；收到换绑回执也清理旧发送积压；以新端口 DAW 回传为准。 |
| P1 | 编辑/删除正在发声的按钮，或删除/移动通道条导致映射变化，原音符没有 Off。 | 跟踪本机实际触发的按钮映射；变更前释放原 Note/CC，避免把释放发到新映射。 |
| P2 | BLE Host 回调满队列等待 5ms；USB 无限排空与每条 5ms 重试会拖慢另一手机及反向反馈。 | BLE 回调零等待；USB 每轮最多 32 条；每端口每轮最多 8 条清音；原子 event packet 写入失败交给后续循环恢复。 |
| P2 | TinyUSB stream 写接口内部保留共享的半包状态，故障重试和双 cable 交替容易使边界处理复杂化。 | 完整 MIDI 消息编码成一个 4 字节 USB event packet，一次提交。 |
| P2 | 全量影子回放占用唯一 BLE 发送者；缓存跨任务没有一致性保护；布尔回放请求可能在完成时覆盖新请求。 | 每轮回放最多 8 条、失败保留游标重试；缓存短临界区；回放请求使用原子序号，两个端口轮流处理。 |
| P2 | BLE 通知批量发送部分成功就返回 ESP_OK，桥接层误报全量成功。 | 只有整批全部提交成功才返回 ESP_OK，失败显式计数。 |
| P2 | MIDI Clock/Active Sensing 与 CC 同包时，固件把下一时间戳当状态，App 直接丢弃整个通知。 | 固件逐条处理实时消息；App 忽略 UI 不消费的实时消息并继续解析后续 CC。 |
| P2 | 仅扩展广告/扩展扫描排除部分旧手机；广播分配失败与端口回执通知分配失败缺少恢复。 | legacy ADV 放 MIDI UUID、Scan Response 放名称；App legacy 扫描；Host 队列串行管理广播并重试失败；端口回执失败自动重试。 |
| P2 | 自动握手可能抢占尚未 explicit_claim 的现有连接；Host reset 留下旧连接槽。 | 自动认领不抢任何现有连接；只有手动强制切换允许互换；Host reset 清槽并提升代次。 |
| P2 | AtomicFile 不保证并发写安全，取消旧防抖任务后后台磁盘写仍可能重叠；前台服务启动失败被隐藏；主题包含 API27 属性但最低 API26。 | 磁盘读写 Mutex 串行化；服务启动失败展示错误并停止新连接流程；移除越界 XML 属性，由现有兼容 API 设置导航栏。 |

## 验证证据

- 固件：ESP-IDF **5.5.2**，target **esp32s3**，完整构建成功。应用镜像 `562592` 字节，1MB 应用分区剩余约 46%。

- Android：`:composeApp:jvmTest`、`:androidApp:assembleDebug`、`:androidApp:lintDebug` 均成功；**57 项测试，0 失败/错误**。Lint 无错误，保留 6 个非阻塞提示（图标、冗余 API 级别判断等）。
- APK：Android 0.1.1，v2 签名验证通过；本机 Debug 签名。
- 芯片：ESP32-S3 rev0.2，MAC `c4:9e:7e:18:c8:84`，16MB Flash / 8MB PSRAM。烧录串口重新插入后为 `/dev/cu.usbserial-120`。
- 备份：原分区表为 NVS `0x9000+0x6000`、PHY `0xF000+0x1000`、factory `0x10000+0x100000`。已完整备份 `0x0..0x10FFFF`，包含所有已分配区；未备份未分配的其余 Flash。
- 烧录：115200 波特率，bootloader / 分区表 / 应用均显示 `Hash of data verified`。较高波特率在本机出现串口噪声错误，因此未采用。
- 启动：USB 初始化、BLE 初始化、广播均成功，无崩溃；日志记录到一台附近中央设备自动连接、MTU256、Notify 订阅和 Port1 握手。
- Mac CoreMIDI：两个独立输入/输出端口均枚举；捕获到两个端口的 CC64/120/123 清音。向两个 USB 端口各发送 100 条 CC；已连接 Port1 的固件统计 `USB->BLE sent=100 drop=0`、`tx_drop=0`。这是 NimBLE 接受通知的统计，不等同于手机 UI 或 DAW 参数已正确应用。
- Mac BLE 自动化尝试：因 **Mac 蓝牙关闭**，Bleak 返回 `Bluetooth device is turned off`，没有运行计划中的 500 条 BLE→USB 100Hz 测试；该项没有标记通过。
- 本机未连接 Android ADB 设备；未安装 APK到手机，未做新 APK 真机手势/后台服务验证。

`panic_fail` 在修复版中累计清音 FIFO 暂时未接受的重试次数。主机尚未打开 MIDI 输入、枚举/串口复位期间可能增长，不等于实际丢失了清音；待发状态保留到成功。串口打开可能复位开发板，硬件测试期间观察到此行为，应避免演出时打开串口监视器。

## 仍需现场确认的因素

1. **两台实际手机同时连接**，A 断线只清 A 端口，B 持续发声不受影响；默认同时认领 Port1、强制换绑、蓝牙反复开关的完整联测。这次只有一台已连接中央设备的启动/握手证据。
2. 新 APK 四指推子与按钮同时操作、默认 MTU 与高 MTU、锁屏/后台/省电模式，至少 30 分钟；液态玻璃 UI 的帧耗时与不同手机蓝牙栈差异需要真机测量。
3. 实际 DAW（Ableton）的 MIDI Map、双端口路由、Note Off、14-bit 参数反馈以及原生 USB 拔插/挂起恢复。本次没有操作 Ableton 工程。
4. 无线拥塞/距离/人体遮挡、手机电源策略、USB 数据线/Hub 接触与供电属于现场不稳定来源；本机串口高波特率错误已有证据，烧录已降速。
5. **现有 BLE 协议仍无配对绑定/鉴权**：附近其他客户端可以占用连接槽或发送控制/强制换绑。此次没有加入会改变配对流程的 bonding/授权体系；正式公开场合应把这项作为后续设计任务。演出前确认两台都是自己的设备。
6. 普通长 SysEx 不转发；App UI 忽略实时消息，未增加完整系统消息编辑能力。复杂第三方 MIDI 数据流仍需专门兼容性验证。
7. 过载恢复优先保证释放音符：极端拥塞时可能短暂清音并丢弃该端口不完整积压，不能承诺所有 Note On 或推子中间值均不丢失。
